# 多引擎文本 Hook 适配 — 架构设计

> 面向 GalGame 注入链路的下一个阶段：从「能把 DLL 注进去」走到「能稳定拿到游戏正在显示的文本」。

---

## 1. 要解决的问题

现有注入器解决了**投送**问题：挂起启动 → 注入 → 恢复运行 → 调用导出函数初始化。
但拿不到文本。而不同 GalGame 引擎的文本输出路径完全不同：

| 引擎类型 | 文本输出方式 | 典型代表 |
| --- | --- | --- |
| GDI 系 | `TextOutA/W`、`ExtTextOutA/W`、`DrawTextA/W` | BGI、多数老引擎、部分 RealLive |
| 自绘 + GDI 混合 | 引擎自己排版，最终仍落到 GDI 输出 | 相当多的日系商业引擎 |
| DirectX 系 | 字形渲染成纹理，走 D3D 绘制 | 后期 KiriKiri、部分新引擎 |
| 引擎私有 | 引擎内部函数产出文本，渲染完全自管 | KiriKiri（TJS 层）、Artemis 等 |

**结论：不存在一个万能 hook 点。** 必须做成「**一套 Hook 框架 + 可插拔的引擎 profile**」，
新增引擎 = 新增一份 profile，而不是改框架。

---

## 2. 分层设计

```
┌──────────────────────────────────────────────────────────┐
│  TextHookClient.exe / 翻译工具 / 任何管道消费者            │  ← 消费层
└───────────────────────▲──────────────────────────────────┘
                        │ 命名管道 \\.\pipe\GalToolText[.<pid>]
┌───────────────────────┴──────────────────────────────────┐
│  Sink（输出通道）                                          │
│    · 管道服务端（后台线程 + 连接管理）                      │
│    · 可选文件落盘（log=1，便于无客户端时验证）              │
│    · 去重（同一文本 N ms 内只发一次）                       │
└───────────────────────▲──────────────────────────────────┘
┌───────────────────────┴──────────────────────────────────┐
│  Extractor（文本提取 + 编码转换）                           │
│    · 按 profile 声明从 hook 上下文取文本（参数下标 / 指针）  │
│    · SJIS(932) / GBK(936) / UTF-8(65001) → UTF-16 → UTF-8  │
│    · 过滤：长度阈值、空白、控制字符                         │
└───────────────────────▲──────────────────────────────────┘
┌───────────────────────┴──────────────────────────────────┐
│  HookEngine（挂钩执行层）                                   │
│    · IAT Hook（一阶段，默认）                               │
│    · Inline Hook（二阶段，需长度反汇编）                    │
│    · VTable Hook（三阶段，DirectX / C++ 虚函数）            │
└───────────────────────▲──────────────────────────────────┘
┌───────────────────────┴──────────────────────────────────┐
│  EngineProfile（引擎适配表）— 唯一的「引擎相关」部分         │
│    · 挂钩目标清单（模块!函数 + 挂钩方式）                    │
│    · 编码、文本提取规则、去重参数、匹配提示                  │
└──────────────────────────────────────────────────────────┘
```

**框架不认引擎，profile 才认引擎。** 这是整个设计的核心约束。

## 3. EngineProfile 抽象

```c
typedef struct {
    const char* module;     // "gdi32.dll"
    const char* func;       // "TextOutA"
    int         kind;       // HOOK_IAT / HOOK_INLINE / HOOK_VTABLE
    int         textArg;    // 文本在第几个参数（0 基）
    int         lenArg;     // 长度在第几个参数；-1 = 以 \0 结尾
} HookTarget;

typedef struct {
    const char*  name;          // "kirikiri" / "bgi" / "generic-gdi"
    UINT         codepage;      // 932 / 936 / 1200
    HookTarget   targets[16];
    int          targetCount;
    int          minLen;        // 短于此长度的文本丢弃（滤噪）
    DWORD        dedupMs;       // 去重窗口
    const char*  hintClass;     // 可选：窗口类名提示，用于 auto 识别
    const char*  hintExe;       // 可选：进程名提示
} EngineProfile;
```

### 内置 profile（一阶段随 DLL 编译进去）

| profile | 编码 | 挂钩目标 | 说明 |
| --- | --- | --- | --- |
| `generic-gdi` | 自动探测 | `gdi32!TextOutA/W`、`ExtTextOutA/W`、`DrawTextA/W` | **万能兜底**，覆盖面最广，先跑通再针对性优化 |
| `generic-gdi-sjis` | 932 | 同上 | 日文原版游戏，强制 Shift-JIS |
| `generic-gdi-gbk` | 936 | 同上 | 中文汉化版，强制 GBK |
| `generic-unicode` | 1200 | 只挂 `*W` 系列 | 已用宽字符输出的引擎 |

> 真实引擎 profile（KiriKiri / BGI / RealLive / Artemis…）需要**对着实机样本逆向**才能填出
> 正确的 `module!func` 与参数布局——这部分必须一台游戏一份地做，无法凭空推测。

### 3.1 实现现状与上面这张图的差距

上面是**目标形态**。当前 `TextHookDll.c` 里实际落地的 `HookTarget` / `EngineProfile` 是它的子集：

| 字段 | 状态 | 说明 |
| --- | --- | --- |
| `module` / `func` / `kind` | ✅ 已实现 | `kind` 目前只有 `HOOK_IAT` |
| `name` / `codepage` / `minLen` / `dedupMs` | ✅ 已实现 | 可外部化，见 §3.2 |
| `textArg` / `lenArg` | ✅ 已实现（S3 完整版） | ini 里的 `text=` / `len=` 直接声明「第几个参数是文本、第几个是长度」；未声明时退回编译期写死的 6 个专用提取器 |
| `argc` / `wide` / `conv` | ✅ 已实现 | 参数总数（1..8）、文本是 `wchar_t*` 还是 `char*`、调用约定（`stdcall` / `cdecl`） |
| `hintClass` / `hintExe` | ❌ 未实现 | `auto` 识别尚未落地，只能靠 `engine=` 显式指定 |

**这张表是理解 S3 能力边界的关键**：`textArg` / `lenArg` 外部化之后，文件 profile
不再局限于框架已知的 6 个函数——只要写清楚参数位置，任何导出函数都能挂。
仍然做不到的是「自动猜出参数位置」（`hintClass` / `hintExe` 那两行），
以及不做句子重组、不覆盖 DirectX 自绘。

### 3.2 外部化后的 profile 文件（S3）

DLL 从**自身所在目录**读取 `TextHookDll.profiles.ini`，也可用
`-exportarg "...|profilefile=<路径>"` 指定别处，或用 `nofile=1` 完全禁用。

```ini
[my-game-jp]
desc=某日文原版游戏
codepage=932
minlen=3
dedup=400
hook=gdi32.dll,TextOutA
hook=gdi32.dll,ExtTextOutA
hook=user32.dll,DrawTextA
```

框架不认识的函数也能挂——补上参数位置即可（序号一律 **1 起**）：

```ini
[my-engine]
desc=引擎自己的文本函数
codepage=932
minlen=2
dedup=200
text=1
len=2
argc=4
wide=0
conv=stdcall
hook=myengine.dll,RenderText
```

| 键 | 含义 |
| --- | --- |
| `text=` | 第几个参数是文本指针（1 起）。**写了它就走通用转发器**，不再依赖编译期的 6 个专用提取器 |
| `len=` | 第几个参数是字节/字符数（1 起）。不写表示文本以 `\0` 结尾 |
| `argc=` | 该函数的参数总数（1..8）。**必填**——转发调用必须知道弹多少字节栈 |
| `wide=` | `1` = 文本是 `wchar_t*`（UTF-16，直接上报）；`0` = `char*`（按 `codepage` 转） |
| `conv=` | `stdcall`（默认，绝大多数 Win32 API）或 `cdecl` |

这几个键可以写在任意 `hook=` 之前或之后，整段读完再统一填进该段的每个 target。
校验是「全有或全无」：`argc` 越界、`text`/`len` 超出 `argc`、值不是数字，
都会让整份文件不生效并退回内置 profile（半个 profile 生效比完全没生效更难排查）。

规则：

| 项 | 行为 |
| --- | --- |
| 同名覆盖 | 文件里的 `[generic-gdi]` 会覆盖内置的那一个，可用来调兜底行为 |
| 全有或全无 | 任何一行出错则整份文件不生效、退回内置 profile，并在启动横幅说明原因 |
| 未实现的方式 | `hook=...,inline` / `hook=...,vtable` **报错**而不是忽略（避免误以为挂钩装上了） |
| profile 名 | 必须 ASCII。`engine=` 参数是 UTF-16、比对时按 `CP_ACP` 转窄，而文件是 UTF-8，非 ASCII 名必然对不上 |
| 未知键 | 忽略，给前向兼容留空间 |
| 可观测性 | 启动横幅单独一行报告「读了哪个文件、加载了几个、叫什么」；`engine=` 写错时告警列出全部可用名 |

**按地址匹配 IAT 槽**：挂钩时不再用「模块名 + 函数名」去比对导入表，而是先
`GetProcAddress` 拿到真实地址，再遍历各模块导入表找**值等于该地址**的槽。
这样 API Set 转发（`api-ms-win-*`）、名字修饰（`_TextOutA@20`）、大小写差异
全部自动兼容——按名字比对时这些情况会整片匹配不到，表现为「profile 明明对了却抓不到」。

## 4. Hook 策略分层

### 一阶段：IAT Hook（本次实现）

改目标模块导入表（IAT）里对应函数的地址，指向自己的实现，原地址存起来供转发。

- ✅ **不需要反汇编、不需要长度解码器**，实现可靠，不会被指令边界问题坑死
- ✅ 对目标进程零破坏性，卸载时还原即可
- ⚠️ **只覆盖走 IAT 的调用**：如果引擎用 `GetProcAddress` 拿指针再调，IAT 里看不到
  —— 已用「挂钩 `GetProcAddress` 本身」补上大部分（见下）

对多数 GDI 系引擎，引擎是静态链接 gdi32 并走 IAT 的，**一阶段足以拿到大部分文本**。

#### 一阶段补充：挂钩 `GetProcAddress` 覆盖动态取址

引擎动态取址时是这样写的：

```c
auto p = (pTextOutA)GetProcAddress(GetModuleHandleA("gdi32.dll"), "TextOutA");
p(hdc, x, y, text, len);     // 导入表里根本没有 TextOutA，IAT Hook 抓不到
```

既然不能改函数入口的指令字节（那需要长度反汇编器），就改**取址这一步**：
把所有模块 IAT 里的 `GetProcAddress` 换成自己的替身，替身先问真实地址，
再查「这个地址是不是我们挂钩的目标」，是就返回我们的替换函数。

- ✅ 仍然只改 IAT 槽，与既有机制完全同构，不需要碰任何指令字节
- ✅ 启动横幅会单独报告「已登记 N 个目标，替换了 M 个 GetProcAddress 槽」，
  这样「钩子挂上了却没抓到文本」时能立刻区分是不是动态取址
- ⚠️ 仍有一个缺口：若引擎连 `GetProcAddress` 都是自己从 kernel32 现取的
  （即不通过导入表），这条也拦不住 —— 那种情况只能上 Inline Hook

### 二阶段：Inline Hook（后续）

在函数入口写 `jmp`，把被覆盖的指令搬到跳板（trampoline）里执行后再跳回。

- ✅ 覆盖所有调用方式，包括 `GetProcAddress` 动态解析
- ❌ **必须正确判断被覆盖字节里的完整指令长度**（x86 变长指令）——
  要么内嵌一个轻量长度反汇编器，要么用 `hde`/`Zydis` 之类的库，但本项目坚持零第三方依赖，
  所以需要自己写一个覆盖常见 prologue 的最小长度解码器

### 三阶段：VTable Hook（DirectX 系）

对 D3D 系引擎，文本不以字符串形式经过任何 API，必须挂在绘制层或直接读引擎内存。

- 这类引擎更适合**换思路**：不打 API 的主意，改从引擎的文本缓冲区读（需要逆向定位结构体）

## 5. 编码转换

GalGame 文本编码情况：

| 场景 | 编码 | Win32 代码页 |
| --- | --- | --- |
| 日文原版（绝大多数） | Shift-JIS | 932 |
| 中文汉化版（老游戏） | GBK / GB2312 | 936 |
| 中文汉化版（新引擎） | UTF-8 或 UTF-16 | 65001 / 1200 |
| 韩文 | EUC-KR | 949 |

处理路径：`MultiByteToWideChar(cp, ...)` → 内部统一 UTF-16 → 输出时 `WideCharToMultiByte(CP_UTF8, ...)`。

**`*A` 系列函数拿到的就是原始字节，编码由 profile 声明**——这是 profile 里 `codepage` 字段存在的原因。
`*W` 系列已经是 UTF-16，跳过转换。

> 坑：`MultiByteToWideChar` 对非法序列会静默替换，可能出现乱码但不报错。
> 一阶段先接受；后续可加「转换失败率」统计，用于自动纠正 codepage 猜测。

## 6. 输出通道：命名管道

选管道而不是文件/共享内存的理由：

- **流式**：翻译工具需要实时拿到文本，不能等文件 flush
- **零依赖**：`CreateNamedPipe` 是 Win32 原生，不需要额外组件
- **天然多客户端**：可以同时挂多个消费者

**协议**（按行分隔，UTF-8，`\t` 分隔字段）：

```
GalToolText\t<pid>\t<hook>\t<text>\n
```

例：
```
GalToolText	41016	TextOutW	こんにちは
```

- 管道名：`\\.\pipe\GalToolText`（默认，可用 `pipe=` 覆盖）；多开场景建议 `pipe=GalToolText.<pid>`
- 服务端由 DLL 在 `InstallConfig` 时创建，后台线程循环 `ConnectNamedPipe`
- 写失败（客户端断开）→ 关闭实例、重新 accept，不影响游戏运行
- **多实例（默认 4 个）**：每个实例一个 accept 线程，各自持有自己的连接；
  同一行文本**广播**给所有已连接的消费者。这样翻译工具和日志脚本可以同时挂着，
  不必互相抢连接。某个实例的客户端断开只会让它自己重建，不影响其它消费者
- **客户端侧要自己处理断线**：服务端重建实例时，消费者手里的句柄就失效了。
  `TextHookClient` 的做法是断开后重新 `ConnectPipe`（最多等 60 秒）并丢弃可能读到的一半行，
  而不是直接退出——否则游戏一重开、或四个实例被别的客户端占满，客户端就会自己消失，
  看起来像「工具坏了」。`ERROR_PIPE_BUSY` 用 `WaitNamedPipe` 等，其余错误码才 `Sleep` 轮询

**去重是必须的**：游戏每帧重绘文本，同一句话每秒可能触发 60 次。
`dedupMs` 窗口内相同文本只发一次（默认 200ms），否则管道会被瞬间打爆。

## 7. 与现有注入器的集成 — **零改动**

这是这套设计最舒服的地方：现有注入器**已经具备**所需的一切能力。

```bat
:: 启动游戏 + 注入文本 Hook DLL + 下发引擎配置，一条命令
DllInjector-x64.exe -inject "游戏.exe" TextHookDll-x64.dll ^
    -export InstallConfig -exportarg "engine=generic-gdi|cp=932|pipe=GalToolText|log=1"
```

复用到的既有机制：

| 现有能力 | 在文本 Hook 中的角色 |
| --- | --- |
| 多 DLL 批量注入 | 文本 Hook DLL 与游戏 MOD DLL 可一起注入，顺序可控 |
| `-export InstallConfig` + `-exportarg "k=v\|k=v"` | **配置下发通道**——profile 选择、编码、管道名全靠它 |
| 启动时注入（挂起 → 注入 → 恢复） | DLL 在目标**挂起状态**下就被加载，DllMain 已执行；但挂钩动作由导出函数完成，见下方「执行顺序」说明 |
| `-injectpid` / `-injectname` 批量注入 | 对已运行的游戏补挂 |
| PE 体检 / 位数校验 | 提前拦掉位数不符、缺重定位段的 DLL |
| 手动映射注入（`-method mm`） | 反调试较强的引擎可用，不落盘、不进模块列表 |

**不需要给注入器加任何代码。** 注入器保持「通用投送器」定位，
引擎适配知识全部沉淀在 profile 里——这也符合它现有的单文件、零依赖设计。

### 执行顺序：挂钩动作发生在游戏开跑之后

读 `InjectorCore.Run` 的实际流程，顺序是这样的：

```
CreateProcess(SUSPENDED) → 逐个 LoadLibraryW 注入 DLL → ResumeThread → 调用导出函数(InstallConfig)
                                                          ▲                ▲
                                                     游戏开始运行      挂钩在这里才装上
```

即**恢复主线程发生在调用导出函数之前**（`ResumeThread` 在 `try/finally` 的 finally 里，
导出函数调用在 finally 之后）。因此：

- 挂钩完成前，游戏已经跑了一小段（实测量级约几十到一两百毫秒，取决于游戏启动开销）
- 这段窗口内输出的文本**抓不到**

**实际影响很小**：GalGame 启动后先出 logo / 厂商动画，第一句对白通常在数秒之后，
一百毫秒的缺口不会漏掉对白。

**若要彻底消除该缺口**，有两条路（都属于 S2）：

1. **在 `DllMain(DLL_PROCESS_ATTACH)` 里装挂钩**——此时进程仍挂起，能赶在游戏执行第一条指令前完成。
   但 DllMain 持有加载器锁，**不能**调用 `CreateToolhelp32Snapshot` 这类内部会取加载器锁的 API
   （会死锁），只能安全地做「主 EXE 的 IAT 补丁」这类纯内存写。而且此刻配置尚未下发，
   编码只能先按系统 ANSI 猜——需要把早期捕获的**原始字节**缓存下来，等 `InstallConfig` 给出 codepage 后再转换。
2. **改注入器，让导出函数在 `ResumeThread` 之前调用**——最干净，但会改变现有工具的行为
   （某些 DLL 的导出函数可能依赖目标进程已在运行），需要谨慎评估，建议做成可选开关。

当前实现选择**先接受这个缺口并把限制写清楚**，而不是塞一个半可用的 DllMain 挂钩进去。

## 8. 路线图

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| **S1** | 框架骨架 + IAT Hook + 编码转换 + 管道输出 + `generic-gdi` profile | ✅ 已实现 |
| **S2** | 最小长度反汇编器 + Inline Hook，覆盖「连 `GetProcAddress` 都自己现取」的引擎 | 待做 |
| **S3** | 外部化 profile（INI 文件，改引擎适配不用重编译 DLL），含 `textArg` / `lenArg` 参数位置外部化 | ✅ 已实现 |
| **S4** | 具体引擎 profile：对实机样本逆向填 `module!func` 与参数布局 | 待做（需样本） |
| **S5** | VTable / DirectX 系适配，或改用「读引擎文本缓冲区」路线 | 待做 |

S3 完成后，profile 已从编译期挪到运行期：适配新引擎只要写一个文本文件，
不用重新编译、也不用重新分发 DLL。S3 外部化了四样东西——挂哪些函数、用什么编码、
去重与长度阈值、**以及「第几个参数是文本 / 长度、参数总数、窄宽字符、调用约定」**。
所以「框架不认识的函数」现在也能挂，只要在 ini 里写清参数位置（见 §3.2）。

仍然留在编译期的是**怎么把取到的字节变成一句完整的话**：句子重组、逐字显示的合并、
DirectX 自绘的读取路径——这些属于 S4 / S5。

## 9. 已知限制

标题里原先写的是「一阶段」，但那已经是过去时——下面这些条目现在横跨 S1（IAT）、
S3（profile 外部化）与 S2（尚未实现的 Inline Hook）。逐条标注了当前状态，
被划掉的是已经修掉的，留着是为了说明「为什么当初会踩」。修掉的条目都带回归防线说明。

- **启动后有一小段抓不到**：注入器的 `ResumeThread` 早于导出函数调用，
  挂钩装上之前游戏已跑了几十到一两百毫秒，这段文本会漏（详见第 7 节「执行顺序」）
- ~~**只覆盖 IAT 调用**：走 `GetProcAddress` 的引擎抓不到~~（**已部分修复**）：
  `GetProcAddress` 本身也被挂钩（见 §4「一阶段补充」），引擎通过导入表调用它时会拿到
  我们的替身。**仍漏**的情形是「连 `GetProcAddress` 都自己从 kernel32 现取」——那只能上 S2
- ~~**profile 文件只能「挑函数」，不能「加函数」**~~（**已修**）：
  `textArg` / `lenArg` / `argc` / `wide` / `conv` 外部化之后，文件里只要写清
  「第几个参数是文本、第几个是长度、一共几个参数、窄还是宽、什么调用约定」，
  框架不认识的导出函数也能挂（走通用转发器，8 个参数上限、两种调用约定）。
  代价是**参数位置得自己数准**——数错不是「抓不到」，而是把整数当指针读，
  目标进程会直接访问违例。所以 ini 里写新函数时，建议先用一个已知会走这条路的
  小样本验证，别直接在游戏里试
- ~~**导入表按模块名精确匹配**~~（**已修**）：改成**按地址匹配 IAT 槽**——
  先解析出目标函数的真实地址，再遍历各模块的导入表，把「值等于该地址」的槽全部替换。
  于是 `api-ms-win-*` API Set 间接导入、以及 `_TextOutA@20` 这类名字修饰都不再影响命中，
  同一个函数在多个模块里被导入也能一次全挂上
- **对运行中的进程补挂存在竞态**：IAT 补丁是逐槽写入的，目标进程此刻正在运行，
  极小概率命中「刚好读到半更新的导入表」。写入本身已改成
  `InterlockedExchangePointer` 并保持页面可执行（RWX 写入、写完立刻还原原保护属性），
  把「写缓冲推迟到 VirtualProtect 之后」这条最容易出事的路径堵上了；
  但**逐槽之间仍不是原子的**，启动时注入（挂起态）无此问题
- **`auto` 识别尚未实现**：`hintExe` / `hintClass` 只出现在上面那张目标形态图里，
  实际 `EngineProfile` 结构体中并没有这两个字段，`ApplyConfig` 里也没有任何按进程名 /
  窗口类名匹配的逻辑——所以现在必须靠 `engine=` 显式指定 profile（不指定就用
  `generic-gdi` 兜底）。真正的引擎识别需要更多样本特征（资源段特征、字符串特征、
  模块列表特征），属于 S4
- **不做文本合并**：GalGame 常把一句话分多次输出（逐字显示），一阶段按次上报，
  句子重组交给消费端
- ~~**管道单消费者**~~（**已改**）：服务端默认创建 4 个实例，同一行文本广播给所有消费者；
  某个消费者连上却不读，只会拖慢它自己那一份写（2 秒超时后标记断开），不影响其它人
- ~~**管道线程在无人连接时会漏掉一个线程和一个管道实例**~~（**已修**，见下）：
  原实现里 `ConnectNamedPipe` 用的是阻塞句柄，`StopHooks` 的 1 秒有界等待超时后只
  `CloseHandle` 了**线程句柄**——关线程句柄不会终止线程，于是该线程与它持有的管道实例
  一直留着。后果比"漏一个线程"严重得多：残留实例占着 `\\.\pipe\<name>`（`nMaxInstances=1`），
  **下一次安装的 `CreateNamedPipeA` 必然失败**，表现为「卸载再重装之后管道再也传不出一个字节」；
  而且那个线程之后还会去碰已经被 `DeleteCriticalSection` 删掉的临界区。
  修法（三处，互相独立）：
  1. 管道改用 `FILE_FLAG_OVERLAPPED` 打开，`ConnectNamedPipe` 挂起后用
     `WaitForMultipleObjects(连接完成事件, g_stopEvent)` 等待 —— 停止信号能立刻打断它；
     相应地 `WriteFile` 也必须走重叠方式（对重叠句柄传 `NULL lpOverlapped` 是未定义行为）
  2. 临界区与停止事件改成「建一次就不销毁」；只有当两个工作线程都确认退出后才关闭事件
  3. 有界等待从 1s 放宽到 2s，并显式区分「线程真的退出了」与「超时了」
  回归防线：`TestTextHook` 场景 5（见 §10）——反向验证确认它在修复前的代码上会 FAIL
- **不做翻译**：本层只负责「把文本拿出来」，翻译与回填是消费端的事
- **DirectX 系引擎无解**：一阶段完全不覆盖

## 10. 验证方式

分两层：**自动化进程内验证**（日常回归，一条命令）与**手工跨进程验证**（贴近真实注入链路）。

### 10.1 自动化：`TestTextHook`（主）

```bat
:: 编译两个架构，然后自动跑两个架构的验证
test\TextHookDll\build.bat
```

`build.bat` 编译完成后会自动执行 `TestTextHook-x64.exe` 与 `TestTextHook-x86.exe`，
任一架构失败即打印 `VERIFY_FAIL` 并以非零码退出。所以「x86 和 x64 都要测试」是命令保证的，
不是人工约定。

`TestTextHook` 把整条链路收进**一个进程**：自己 `LoadLibrary`、自己调 `InstallConfig`
装钩子、自己用 GDI 输出文本、自己读 `texthook_log.txt` 判断结果。它跑的 7 个场景：

| 场景 | 目的 |
| --- | --- |
| 1 内置 `generic-gdi` | 基线：6 个函数都能抓到，SJIS → UTF-8 正确 |
| 2 文件 profile 只挂 `TextOutA` | **S3 是否真正生效的关键断言**——`TextOutW` 不该被抓到 |
| 3 故意写错的 profile 文件 | 全有或全无：应整份退回内置，且仍能抓到文本 |
| 4 随仓库分发的模板 ini | 保证分发出去的模板本身可用 |
| 5 命名管道 | **唯一覆盖管道主链路的场景**，见下 |
| 6 动态取址 | **唯一覆盖 `GetProcAddress` 替身的场景**，见下 |
| 7 通用转发器 | **唯一覆盖 `text=` / `len=` / `argc=` 的场景**，见下 |

场景 1–4 都只靠 `texthook_log.txt` 判断结果，全程没有客户端连管道——也就是说
**管道线程的生命周期一直没被验证过**。场景 5 补上这一块：

- 作为客户端真的连上管道，真的从管道里读到文本（SJIS → UTF-8 内容正确）
- 第二个消费者也能连上，并且也收到了同一行——管道是多实例的，行为是广播而不是独占
- `Unhook` 后管道实例必须已释放：用「自己按 `nMaxInstances=1` 建同名实例能否成功」
  来判断，比猜线程数直接得多
- 反复「无客户端安装 → 卸载」后管道名仍然空闲、线程数回到本轮基线

> 这三条断言抓出了「管道线程卡死在 `ConnectNamedPipe`、重装后管道永久失效」的缺陷。
> 反向验证（把修复前的源码编成独立 DLL 再跑同一个测试）确认场景 5 在修复前 **FAIL**，
> 且第 3 条是真正有区分力的那条——第 2 条在修复前后都 PASS（因为那时客户端已经连过，
> 线程走的是正常释放路径）。**只写能通过的断言等于没写断言。**

> 线程数基线取在场景 5 内部、不取在进程启动时：GDI 首次使用（`GetDC`）会让系统懒加载
> 一个线程、把进程线程数永久抬高 1，拿它当基线会误报成"泄漏"。

场景 6 针对 `GetProcAddress` 重定向（见 §4「一阶段补充」）。它必须真的**走动态取址这条路**，
否则等于没测：先记下 `GetProcAddress(hGdi, "TextOutA")` 的**原始**返回值，装钩子后断言
再取一次拿到的是**另一个地址**、且落在 DLL 映像范围内；然后用这个动态拿到的地址**真的调一次**，
断言文本被捕获；最后 `Unhook` 之后断言又回到原始地址。只检查"替换表里有条目"是不够的——
真正会出问题的是「表填好了但替身没被调用」或「卸载后表没清干净，引擎拿到野指针」。

断言覆盖：无修饰导出名可取（x86 `.def` 的回归防线）、启动横幅内容、编码转换正确、
profile 对挂钩集合的实际约束、**卸载后主 EXE 的 IAT 已完全还原**
（逐槽检查有没有地址落在 DLL 映像范围内）。

场景 7 针对 `text=` / `len=` / `argc=` 这条通用转发器路径。这是 S3 完整版里**最危险的一段**：
它按「参数个数 × 调用约定」生成 128 个 thunk，写错一个就是弹歪栈，而失败方式是**崩溃**
而不是「抓不到文本」——所以必须真的调一次，光看启动横幅报"挂上了 N 个槽"没有意义。

取巧之处：拿框架**本来就认识**的 `TextOutA` 来测，但 profile 里故意写
`text=4 / len=5 / argc=5 / wide=0 / conv=stdcall`，于是挂钩走的是 `t->textArg > 0` 分支——
与「框架不认识的函数」完全同一条代码路径，不必编一个测试 DLL 就能验证真实参数布局。

> 这个场景上线后立刻在 x86 上炸了，而 x64 全绿。根因是 `conv=` 的解析写反了
> （`stdcall` 被置成 1，而 1 的语义是 cdecl），x86 上弹栈方向相反直接访问违例；
> x64 只有一个调用约定，所以这个错误在 x64 上永远看不出来。
> **这就是为什么同一个测试必须跑双架构——单架构测试只能证明"这条路径在这个 ABI 上没写错"。**

> 最后那条断言是有来历的：它抓出了「主 EXE 被重复挂钩 → 卸载时把 IAT 槽还原成
> 我们自己的替换函数」这个缺陷——`Unhook` 恒返回 1，光看返回值完全看不出来。
> 这也说明**验证要检查副作用，而不是检查返回值**。

`TestTextTarget` / `TestTextHook` 都用**硬编码字节数组或 `\uXXXX` 转义**写期望文本，
不含任何非 ASCII 字面量，因此「抓到的文本对不对」与源码文件编码无关。

### 10.2 手工：跨进程真实注入链路（补充）

自动化测试走的是 `LoadLibrary`，而真实链路走的是注入器，值得偶尔手工确认一次：

```bat
:: 1. 起客户端监听管道
test_output\TextHookClient.exe

:: 2. 注入并启动目标程序（目标程序会主动用 GDI 输出日文/中文文本）
DllInjector-x64.exe -inject test_output\TextTarget_x64.exe test_output\TextHookDll-x64.dll ^
    -export InstallConfig -exportarg "engine=generic-gdi|cp=932|log=1"
```

预期：客户端实时打印捕获到的文本，同时 `texthook_log.txt` 落盘一份。

注意 `cp=` 是**进程级**的，一个进程只能有一种 `*A` 编码。`TextTarget` 默认输出 Shift-JIS；
要跑 GBK 就 `TextTarget_x64.exe gbk` 并传 `cp=936`。两者不匹配时 `*A` 文本必然乱码，这是设计使然。

### 10.3 验证 profile 文件是否真的被读到

看 `texthook_log.txt` 开头的启动横幅，它有两行：

```
[TextHookDll] 已安装 profile=my-game-jp  cp=932  挂钩槽=8  管道=\\.\pipe\GalToolText  PID=1234
[TextHookDll] profile 文件 D:\...\TextHookDll.profiles.ini 已加载 2 个：my-game-jp, my-game-cn
```

第二行直接回答「我改的那个文件到底有没有被读到、里面的 profile 认出来了没有」。
